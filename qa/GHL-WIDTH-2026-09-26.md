# Contact iframe width correction

## Embed and ancestor audit

`components/contact.tsx` renders a cross-origin iframe directly and loads GHL's `form_embed.js` helper. It is not inline form HTML. No form-internal CSS was added or modified.

Ancestor chain: iframe → `.contact-embed` → `.contact-form-card` → `.container.contact-grid` → contact section → main → body → html. The near-even grid split was the main desktop width constraint; the preceding tablet layout also capped the form card at 720px. Ancestors had no transform scaling or overflow clipping that narrowed the form. The iframe itself retains its normal browser overflow behavior.

Only `app/responsive.css` implements this fix:

- Below 1200px, contact columns stack.
- At 1200px and above, columns use `minmax(300px, .65fr) minmax(760px, 1.35fr)` with a 36–48px responsive gap.
- Form card: width 100%, min-width 0, max-width 940px; desktop padding 24px, smaller-screen padding 8px.
- The 720px tablet cap is removed.
- Embed wrappers have width 100%, min-width 0 and no max-width. The iframe has width 100% and max-width none. Only the iframe element is styled, not its document.
- Required iframe heights, URLs, IDs, mappings, submission handling, locale routes and Cloudflare settings are unchanged.

## Computed widths

Rounded CSS pixels measured in the production preview. EN/ES/IT produced the same widths. The grid's right track and the form-card wrapper differ at 1920px because the card stops growing at 940px. The inner `.contact-embed` width equals the iframe width.

Additional 1199/1200px checks passed the stacking transition without document overflow in all three locales. No horizontal overflow was found at any requested width.

## Provider layout verification and limitation

The embedded iframe remained in its loading state during this browser session, so its live fields could not be visually verified inside the host page. Each unchanged provider URL was also opened directly for a read-only comparison at the actual iframe widths.

All three provider forms showed two columns at 777, 822, 881 and 890px, with the first two input fields sharing a top coordinate and occupying different horizontal positions. At 318px they stacked vertically. Thus no remaining one-column behavior was observed in the provider documents at widths above 850px. This direct comparison does not establish that embedded loading succeeds. No real lead was submitted and no GHL configuration was changed.
